## 3.3 ⚠️ 必查项：目标文件自身的 `.bak` 不在备份集内 —— 确认会留下不一致状态

```
before: target=da88f886b17a  target.bak=0dfaab26a87a（内容 {"hooks":…"echo OLD-BAK-SHOULD-STAY"…}）
假 CLI 行为：target := "THIS IS NOT JSON"；target.bak := "GARBAGE-BAK-CONTENT"；exit 0
$ curl -X POST /api/rtk/toggle {"agent":"codex","on":true,...}   → HTTP 409
after : target=da88f886b17a（byte-identical = YES，回填正确）
        target.bak=c91d7c0efbb1 = "GARBAGE-BAK-CONTENT"
        target 与 .bak 一致？ NO —— 不一致状态
        控制台备份目录里含 .codex__hooks.json.bak 的数量：0（用户原来的 .bak 世代不可恢复）
```

代码事实：`guardEntries(targetId)`（`server/rtkService.ts:640-656`）只收集**其它** agent 的
`hookFile`、`hookFile.bak` 与 extraFiles；`targets` 只有目标自己的 `hookFile` + `extraFiles`。
所以目标自身的 `.bak`：既不在备份里（无法回填/回滚），也不在清理逻辑里（不会被删）。
蓝队自报的遗留**成立**，且后果不是「无害」：用户上一次的 `.bak` 世代被静默销毁，
失败后 `.bak` 还可能与目标文件内容不一致。

建议：把目标的 `hookFile + '.bak'` 也纳入备份集与快照；若 CLI 新建了它，按 extra 文件语义处理。

## 3.4 ⚠️ 新发现（次要但真实）：OFF 路径的写后校验只看「标记是否存在」，文件被写坏也算成功

实例 D（8804，假 CLI：无论参数都把目标写成垃圾并 exit 0）

```
before: target=da88f886b17a（合法 JSON）
$ curl -X POST /api/rtk/toggle {"agent":"codex","on":false,...}   → HTTP 200
{"ok":true,"mechanism":"rtk-cli","backupId":"2026-10-01T01-22-31-488Z","cli":{"exitCode":0,"ok":true}}
after : target=c8b2d783a460  内容="THIS IS NOT JSON"  valid=NO
```

即：`verifyLocalHook(spec, on=false)` 只要求「rtk 标记不存在」就算成功，不校验文件仍是合法 JSON；
而 ON 方向因为要求标记存在，会落到兜底路径并给出 409。方向不对称。
此后用户再点 ON 会得到 409（文件不可解析），但控制台在 OFF 那一步已经报过成功。

对照（真实 rtk）：文件预先损坏时，OFF 与 ON 都会返回 409 `hook_file_unparsable`（诚实）——
说明该缺口只在「CLI 写坏文件且 exit 0」时出现，触发条件较窄（外来/损坏的 RTK_BIN、CLI 崩溃但退出码为 0）。
建议：OFF 成功后也做一次 JSON 可解析性校验，不通过则按失败回填并报错。
