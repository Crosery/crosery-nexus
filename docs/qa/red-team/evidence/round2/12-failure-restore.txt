# 缺陷3：失败路径不还原（rtk CLI 把钩子文件写坏后，控制台报错但把坏内容留在原地）

隔离实例 8792，RTK_BIN=/tmp/cac-r2/fake-rtk-garbage.sh
（该假二进制 --version / gain 正常，执行 init 时把 $HOME/.codex/hooks.json 覆盖为 "THIS IS NOT JSON" 并 exit 0，
用以模拟「CLI 崩溃/被杀/写一半」这类宿主异常）

```
before: bytes=190 valid=yes
        {"hooks":{"PreToolUse":[{"hooks":[{"type":"command","command":"echo third-party-a"}]}]}}

$ curl -s -b cookies-8792.txt -X POST http://127.0.0.1:8792/api/rtk/toggle \
    -H 'Content-Type: application/json' \
    -d '{"agent":"codex","on":true,"plane":"local","confirm":true}'
{"error":"codex 的 .codex/hooks.json 不是合法 JSON，拒绝覆盖","plane":"local","reason":"hook_file_unparsable",
 "backup":"/tmp/cac-r2/home/.agents/crosery/magpie-console/backups/2026-10-01T00-45-15-387Z"}   [HTTP 409]

after : bytes=16  valid=no  内容=THIS IS NOT JSON     ← 备份目录里有合法原件，但没有回填
```

代码路径（server/rtkService.ts:712-738）：

1. `runRtkCli()` 执行 CLI（CLI 把文件写坏，exit 0）；
2. `verifyLocalHook()` 失败 → 走 `hooks-json` 兜底分支；
3. `applyHookJson()` 预检(第 588 行)发现不是合法 JSON → 抛 409 `hook_file_unparsable`；
4. catch 里执行 `writeFileAtomic(filePath, existedBefore)`，而 `existedBefore` 是第 729 行**在 CLI 之后**读的（此时已是坏内容）→「还原」把坏内容写回坏内容；
5. 真正的前置原件只存在于 `backup.dir` 里，响应只给出路径（`error.backup`），没有自动回填，也没有提示可用 `/api/rtk/rollback` 恢复。

对照（真实 rtk，实例 8795，有效文件）：同样的 toggle 返回 200，文件合法且 rtk 条目 = 1。
