# 写入面收口：假内核 socket + 假中转站（本地 HTTP）实测

设施（全部本地，未触碰真实中转站）：
- 假内核：unix socket /tmp/cac-r2/kernel.sock，逐请求追加日志，GET /internal/rtk 返回 200，
  POST /internal/rtk 记一行 `WRITE-REACHED-KERNEL`
- 假中转站：http://127.0.0.1:8796，逐请求追加日志，/api/library/rtk 一律 404（模仿真实 CPA 主机）

## 1) 实例 A（PORT=8795, 默认 GATEWAY_ENGINE=cpa）—— 内核/中转站平面写请求

```
POST /api/rtk/toggle {"agent":"codex","on":false,"plane":"kernel"}
 -> 501 {"error":"内核运行在沙箱 HOME（不含本机 agent 配置），默认只读；确需下发请显式设置 RTK_ALLOW_KERNEL_WRITE=1","plane":"kernel","reason":"kernel_write_not_supported"}
POST ... {"plane":"kernel","confirm":true}
 -> 同上 501（confirm 不改变结论）
POST ... {"plane":"relay"}
 -> 501 {"error":"中转站没有可用的 RTK 写入面（relay_route_missing），控制台不发起写请求","plane":"relay","reason":"relay_write_not_supported"}
POST ... {"plane":"relay","confirm":true}
 -> 同上 501
```

假服务端日志：**0 条写请求**

## 2) 实例 B（PORT=8797, GATEWAY_ENGINE=magpie, 无允许位）

内核平面被真正探测到（假内核可用）：

```
{"plane":"kernel","kernelWriteEnabled":false,"remoteWriteEnabled":false,
 "planes":[{"id":"kernel","available":true,"configured":true,"state":"available","reason":"kernel_rtk_ok"},
           {"id":"relay","available":false,"configured":true,"state":"not_supported","reason":"relay_route_missing"},
           {"id":"local","available":true,"configured":true,"state":"available","reason":"local_host"}]}
POST toggle plane=kernel  -> 501 kernel_write_not_supported
POST toggle plane=relay   -> 501 relay_write_not_supported
```

## 3) 实例 C（PORT=8798, GATEWAY_ENGINE=magpie, RTK_ALLOW_KERNEL_WRITE=1 + RTK_ALLOW_REMOTE_WRITE=1）

```
{"plane":"kernel","kernelWriteEnabled":true,"remoteWriteEnabled":true}
POST toggle {"agent":"codex","on":false,"plane":"kernel","confirm":true}
 -> HTTP 200，ok:true，readPlane:"kernel"，返回的是假内核的读数（path=/fake/rtk, version=9.9.9, agents=[]）
    假内核日志新增：POST /internal/rtk  +  WRITE-REACHED-KERNEL      ← 允许位确实打开了写通道
POST toggle {"agent":"codex","on":false,"plane":"relay","confirm":true}
 -> 仍 501 relay_write_not_supported；假中转站日志里 **没有任何写请求**（route 缺失时写闸门先短路）
```

## 4) 真实中转站（只读）

```
GET https://ai.crosery.com/api/library/rtk                     -> 404
GET https://ai.crosery.com/v0/management/rtk  (无凭据)          -> 401
GET https://ai.crosery.com/v0/management/rtk  (Bearer 管理密钥) -> 404
GET https://ai.crosery.com/v0/management/auth-files (Bearer)    -> 200   # 管理面本身可用
```

## 结论

- 「kernel/relay 平面默认 0 条写请求」**已验证**（假服务端日志 + 501 文案）。
- 「relay 真机没有 RTK 路由、控制台不会对它发写请求」：真机 404 已验证；「不发写请求」由
  同代码同状态（relay_route_missing）的隔离实例实测外推（写闸门在探测为 not_supported 时直接 501，
  不进入 relayRtkRequest），**未对真实中转站做写操作，也未做真机抓包**。
- `RTK_ALLOW_KERNEL_WRITE=1` 后写请求确实会发到内核 socket（内核以沙箱 HOME 运行），
  这与「不下发到中转站那台机器」是两件事，UI 文案已区分（RtkBoard.vue:61/89）。
