## 为什么量

红队第十六轮的容量预演发现报表 loader **随数据量线性增长**，并给出一句可执行的发布判断：

> 发布前先跑一次窗口内 `COUNT(*)`：≤30 万行 ⇒ 全部 <1 秒无风险；≈280 万行 ⇒ 先优化 p95 与 usage-overview 预聚合再发。

这条测量的输入来自**红队合成数据**（100k 行 = 132MB ⇒ 外推生产 3.7GB ≈ 2.8M 行）。Lead 直接用生产库把这个假设换成了实测值。

## 这两条实测如何改变红队的结论

1. **外推高估了**：红队假设 3.7GB ≈ 2.8M 行；实测**全量 96 万行**、30 天窗口 **45 万行**、7 天窗口 **15 万行**。按红队的线性斜率插值，30 天窗口下 usage-overview 约 **1.4s** 而不是 8.9s，7 天窗口约 **0.5s**。
2. **更关键：`usage_hourly_rollup` 在生产里是填充的（34,316 行）**，而红队的合成库里它是**空的**——于是他们测到的是"所有聚合都退回扫 `usage_events`"。实测生产代码里 `usage_hourly_rollup` 出现在 **14 处**（usage-overview、breakdown、client-type、daily、by-day-by-model 等聚合都走它），只有 charts/top-N 与 **p95** 仍然打在 `usage_events`（`INDEXED BY idx_usage_*_rollup`）。
   ⇒ **rollup 支撑的那些聚合，实际扫描量是 ~1.6 万行（30 天占比）而不是 45 万行**，红队的数字对这部分是**悲观**的。
3. **仍然真实的那个点**：**p95** 用 `LIMIT 1 OFFSET (SELECT COUNT(*)*0.95)`（`server/usageReports.ts:60-73`）——它打在 `usage_events` 上，30 天窗口 45 万行意味着要**逐个跳过约 42.7 万个索引项**，且这段子查询在一次调用里出现两次。这条**不受 rollup 帮助**，是红队发现里最值得修的一处。

## 我的判断（供发布决策）

- 红队的"有条件放行"现在可以更确定：**窗口是 45 万行级别而不是 280 万行**，且**最重要的聚合走 rollup**。
- **仍未实测**：生产规模下的真实端到端耗时（需要"生产行数 + 填充的 rollup"的合成库，红队的库缺了后者）。这已派给红队复跑（按实测行数造数 + 灌 rollup）。
- 若复跑仍显示某些接口 >1s，**建议优先优化 p95 子查询**（改窗口函数或预聚合直方图），而不是整体预聚合——因为聚合路径已经有 rollup 了。

## 边界

- 只读查询，**未写入、未修改生产库**；未在生产实例上做任何压测。
- 行数会随时间增长：66 天 ≈ 96 万行 ⇒ 日均约 1.45 万行 ⇒ **30 天窗口每月增加约 45 万行**（若保留策略不清理）。今天是 45 万，一个月后约 90 万——**增长本身就是结论的一部分**。
